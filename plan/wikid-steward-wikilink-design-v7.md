# wikid-steward ＆ SimpleWiki：[[WikiLink]] 処理・セルフヒーリング詳細設計書 (v7.0 / GFM・アセット空間隔離・自律協調版)

本設計書は、人間が Markdown エディタで記述する手軽な `[[WikiLink]]` を起点とし、OKF v0.2 規格が求めるポータビリティと、AI/人間による共同編集を安全かつ高度に支えるための「リンク処理およびセルフヒーリング（自己修復）」に特化した詳細設計である [21, 29]。

特に、人間が身構えずに日常の気づきを書き残せる **「## 📝 手書きメモ」** の絶対保護（HTML非表示タグガード）、過剰リンクの自動抑制、バックリンク関係のクリーンな重複排除、**「GitHub Flavored Markdown (GFM)」への完全な互換性確保**、そして **「まだ定義されていない言葉の使われ方を逆引きスキャンし、LLMを用いてその組織固有の定義レジュメを後追いで自動生成（逆合成）する」** という革新的な自律知識コンパイル仕様を定義する [4, 21]。

さらに、フォルダカオスを防ぐ「スタブ専用フォルダ stubs/ と昇格ライフサイクル」、編集衝突を防ぐ「AI自動ブランチ ＋ PR協調モデル」、および「来歴 sources と GFM Footnotes の静的整合性スキャン」の設計を完全にマージし、アセットフォルダのSlug階層による名前空間の物理的隔離を正確に反映している。

## 1. WikiLink のライフサイクルと役割分担

### 1.1 GFM (GitHub Flavored Markdown) との互換設計
ポータビリティと Git でのホスティング効率を極限まで高めるため、出力・処理される Markdown 形式は **GitHub Flavored Markdown (GFM)** に準拠させる [112]。
* **標準 Markdown リンクへの変換**:
  GitHub のリポジトリビューなど、標準的な GFM レンダラーは Obsidian 固有の `[[WikiLink]]` を直接ハイパーリンクとして解釈できない。そのため、`wikid-steward` によるコンパイル・ビルド時、またはデプロイ用エクスポート時に、`[[用語名]]` を GFM 準拠の標準相対パスリンク `[用語名](/wiki/concepts/用語名.md)` へと自動変換・相互結合する機構（`convert_links.py` 由来のロジック）を維持する [121]。これにより、**GitHub UI上でもリンクを直接クリックしてWikiを快適に巡回可能**になる。

### 1.2 ライフサイクル
```
[ 人間の手動記述 / AIのラフ出力 ]
       │  例: 「[[システムアーキテクチャ]] の設計」
       ▼
[ wikid-steward compile / relink ] (CLI層)
       │  ・ネスト破綻（[[[[...]]]]）を100%回避する1パス置換 [21]
       │  ・セクション別リンク化（大見出し ## ごとに最初の1回のみ WikiLink 化）[21]
       │  ・未作成ページ（赤リンク）に対して OKF v0.2 準拠の「スタブノート」を自動生成 [29, 31]
       ▼
[ Git リポジトリ (Markdown) ] (データ層)
       │  ・GFM (GitHub Flavored Markdown) 互換形式（標準相対リンクへの書き出しに対応）[112]
       ▼
[ SimpleWiki レンダラー ] (閲覧層)
          ・[[WikiLink]] または GFM リンクを HTML のハイパーリンクへ動的に相互変換 [118]
          ・パースされた接続情報から重複を排除した「バックリンク（被リンク）」を自動レンダリング [118]
          ・「未定義スタブノート」に対し、蓄積されたバックリンク文脈から AI が自動で定義レジュメを逆合成 [4]
```

## 2. 堅牢型自動再リンク（Relinker）のアルゴリズム

AIがテキストから専門用語を自動で抽出し、Markdown 内の対応する単語を `[[WikiLink]]` に自動置換（再リンク）する際、単純な文字列置換（`replace`）を行うと、すでにリンクされている部分を `[[[[用語]]]]` のようにネスト破綻させたり、コードブロック内や画像パス、HTMLテーブルを破壊したりする [21]。

これを防ぐため、`wikid-steward` CLI には md-wiki から移植した **1パス最長一致セグメント分離置換アルゴリズム** を搭載する [21]。

### 2.1 処理フロー
1. **保護セグメントの分離（トークナイズ）**:
   Markdown テキストをスキャンし、置換対象から除外すべき「保護エリア」を一時的に特殊なトークン（例: `__PROTECTED_SEGMENT_0__`）に置き換えて退避させる [21]。
   * **保護対象（GFM/マルチメディア対応）**:
     * コードブロック（`` ```python ... ``` ``）およびインラインコード（` `code` `）
     * すでに `[[WikiLink]]` となっている部分、および標準 GFM マークダウンリンク（`[表示名](URL)`）
     * **HTML テーブル (`<table>...</table>`)**: 複雑な SBOM 表などの構造・タグを絶対保護 [25]
     * **Mermaid ブロック (` ```mermaid...``` `)**: 構成図テキストを保護
     * **数式ブロック (`$$...$$`, `$...$`)**: LaTeX 数式内の記号や変数の誤置換を完全に排除
     * **画像アセットパス (`![fig1.png](assets/{slug}/fig1.png)`, `<img src="assets/{slug}/fig1.png">`)**: 各原本ドキュメント（`slug`）ごとにアセット用フォルダが `assets/{slug}/` として名前空間隔離され、異なる資料間での `fig1.png` などのファイル名衝突を物理的に100%防止して配置・維持 [21]
     * YAMLフロントマター領域
2. **最長一致置換**:
   残されたプレーンテキスト領域に対して、登録されている「専門用語（既存 of ノートタイトル一覧）」を **文字数の長い順（最長一致）** にソートして置換を試みる。
3. **過剰リンクの自動抑制（セクション別・ファーストヒット置換）**:
   可読性とアクセシビリティのバランスを考慮し、同一文書内で同じ用語が何度も登場しても、**各大見出し（`##`）で区切られたセクションごとに最初の1回のみ**を `[[WikiLink]]` に置換する（設定 `wikilink.mode: first_hit_per_section` で制御可能）。2回目以降の出現はプレーンテキストのままスルーする。
4. **トークンの復元**:
   退避させていた保護セグメントを元の位置に復元し、安全に結合された Markdown を出力する [21]。

## 3. 「## 📝 手書きメモ」セクションの絶対保護

人間が日常の検証、会議、または実務で得た「現場のリアルな一次情報（暗黙知や実践した記録）」を身構えずにサッと書き残すためのエリアとして、**`## 📝 手書きメモ`** セクションを標準仕様として定義する [8]。

人間がエディタ上でスペースを打ち間違えたり（例：`## 📝手書きメモ`）、見出しハッシュを書き換えたり（例：`### 📝 手書きメモ`）しても、プログラムが 100% 確実に保護領域を検出できるよう、**非表示の HTML コメントタグによる二重防壁（ガードレール）** を適用する。

### 3.1 技術的ガードレール（HTML コメントによるスキャン制限）
```markdown
## 📝 手書きメモ

<!-- HUMAN BEGIN -->
ここに人間がサッと現場メモや検証した事実を追記します。
このエリアは自動コンパイルや逆合成処理時に絶対に破壊・上書きされません。
<!-- HUMAN END -->
```

* **上書き禁止の保護処理**:
  `wikid-steward` はファイルを自律更新する際、`(?s)<!-- HUMAN BEGIN -->.*?<!-- HUMAN END -->` のパターンで囲まれた領域を「人間専用エリア」として丸ごとメモリ上に退避（保護）させた上で、AIの自動合成結果と結合する [8]。
* **メリット**:
  人間の記述の表記揺れによる「メモの意図しない上書き消滅」が物理的に 100% 回避される。

## 4. 被リンク（バックリンク）のクリーンな重複排除

SimpleWiki または `wikid-steward lint` が、知識データベース全体のリンク関係をスキャンしてバックリンク（Cited by）の一覧を表示する際、**「同一文書内の同じ用語への複数リンクは、ユニークな1エッジ（単一の接続関係）として処理し、重複を完全に排除（Deduplication）する」** ロジックを適用する [118]。

### 4.1 重複排除のデータ表現
データベースまたはメモリ上の有向グラフインデックスにおいて、接続マップは文書単位でユニークに集約される。

$$\text{接続表現: } \text{「文書A」} \xrightarrow{\text{Unique Link}} \text{「システムアーキテクチャ」}$$

### 4.2 UI・管理上のメリット
* 1つのノートの詳細画面において、バックリンク一覧を描画する際、重複してリストアップされるのを防ぎ、すっきりした **ユニークな引用元リスト** を提供する [118]。

## 5. 【核心】バックリンク文脈からの「用語定義・解説レジュメ」自動逆合成 (Knowledge Retro-Compilation)

**「人間は定義を意識せず、ただ `[[未定義用語]]` をいろんなノートに書いて文章を綴っておくだけ。文脈が十分に集まれば、AIがハルシネーションを起こさずに、自動であなただけの組織固有の解説ページを裏で組み立ててくれる」** という、逆引きの知識コンパイルフローである [4]。

### 5.1 循環汚染およびハルシネーションを塞ぐ安全基準

AI同士のコピーの繰り返しによる知識の劣化・ハルシネーションの連鎖を防ぐため、以下の3つの安全弁（ガードレール）を徹底する。

1. **最小バックリンク数 \\(N\\) によるトリガー制限**:
   未定義のスタブノート（`status: draft`）に対し、被リンク（ユニークなバックリンク）数が **設定した閾値 \\(N\\) 件（デフォルト：`3`、設定ファイル `config.yaml` の `retro_compilation.min_backlinks` でカスタマイズ可能）に達するまでは自動の定義逆合成（`compile-stub`）を起動させず**、下書きのまま待機させる。これにより、極端に文脈が薄い状態でのAIの推測捏造（ハルシネーション）を未然に防ぐ。
2. **AI生成マークアップの明示 (`generated.by`)**:
   AIが逆合成したページには、OKF v0.2の Actor 仕様に準拠した以下の生成者メタデータを必ず記述する [62, 92]。
   `generated: { by: 'wikid-steward/auto-compiler', at: ISO8601 }`
3. **文脈スキャンソースからの「AI生成物排除」フィルター**:
   他のスタブノートを逆合成するためのバックリンク文脈スキャンを行う際、**`generated.by: 'wikid-steward/auto-compiler'` を持ち、かつ `verified`（人間による査読）が存在しないページを、文脈抽出対象から 100% 除外** する [64]。
   インプットとなる文脈は、以下の「信頼性の高いソース」のみに厳格に制限される。

| ソースのメタデータ状態 | 逆合成コンテキスト（スキャン）への採用可否 | 理由 |
| :--- | :---: | :--- |
| **`verified` に `human:` が存在する** | **採用（推奨）** | 人間が目を通して承認した、最も信頼性の高い情報であるため [64]。 |
| **`generated.by` が `human:<id>`** | **採用（推奨）** | 人間が手書きしたオリジナルの知識であるため [69]。 |
| **`status: stable` かつ AI生成物** | **採用（許容）** | AI生成だが、検証をパスするか人間により `stable`（安定）に昇格されているため [64]。 |
| **`status: draft` かつ AI生成物** | **排除（100%除外）** | まだ検証されていない一時的な下書きスタブであり、ハルシネーション汚染源になるため [64]。 |

### 5.2 多言語統制（Target Language Rule）
インプットとなる文脈ソースに英語・日本語が混在していても、出力する定義解説 Markdown の本文は必ず `config.yaml` で指定された **`llm.target_language`**（例: `"Japanese"`）に厳格に翻訳・統一されて生成されます。

## 6. セルフヒーリングとスタブフォルダ隔離（stubs/）

### 6.1 赤リンクの自動スタブ起票（OKF v0.2 準拠）
`wikid-steward lint` が未作成のリンクターゲット（赤リンク）を検知した段階で、自動で **OKF v0.2 の必要最小限のメタデータを持つ下書きファイルを自動作成** する [29, 31, 87]。

このスタブファイルは、既存の本番用フォルダ（`concepts/`など）を汚染しないよう、**「スタブ専用フォルダ（`wiki/stubs/`）」**に隔離格納して保存されます。

```markdown
---
type: "Concept"
status: "draft"
generated:
  by: "wikid-steward/linter"
  at: "2026-08-14T05:52:52Z"
---

# 存在しない概念

※ 本ページは [[wikid-steward]] のセルフヒーリング機能によって自動的に起票されたスタブ（下書き）です。他のノートでの使われ方（バックリンク文脈）を元に、自動で定義レジュメが生成されるか、手動で加筆されるのを待っています。

## 📝 手書きメモ

<!-- HUMAN BEGIN -->
<!-- HUMAN END -->
```

### 6.2 フォルダ・昇格ルーティング
1. **スタブ状態 (`draft`)**: ファイルは `wiki/stubs/{slug}.md` に置かれ、人間が加筆するか、またはバックリンクが \\(N\\) 件以上溜まるのを待機。
2. **昇格状態 (`stable`)**: 自動逆合成（`compile-stub`）が完了するか、または人間が査読し `wikid-steward review` によって `verified` を付与して status を `stable` に昇格させたタイミングで、CLI は自動的にファイルを本来のルーティング先（例: `wiki/concepts/{slug}.md`）へ移動します。この際、`SimpleWiki` 側のインデックスも自動で再ビルドされます。

### 6.3 タイポ（Typo）あいまい検索サジェスト
人間による打ち間違いに対して、以下のアルゴリズムで修復を支援する。
1. **文字列類似度の算出**:
   赤リンクの文字列（例: `システムアーキてくちゃ`）と、既存の正常なノートタイトル一覧のすべてのタイトルを、**レーベンシュタイン距離（Levenshtein Distance）** または **ゲシュタルトパターンマッチング（SequenceMatcher）** で比較する。
2. **類似判定基準**:
   類似度（0.0 〜 1.0）が **`0.75` 以上** のタイトルが存在するか判定する。
3. **挙動の定義**:
   * **`lint --dry-run` 時 / CLI警告時**:
     `"警告: リンク切れ [[システムアーキてくちゃ]] が見つかりました。既存の [[システムアーキテクチャ]] のタイポである可能性があります。"` とコンソールに出力する。
   * **手動/AI修復コマンド（`wikid-steward resolve` 等）**:
     タイポを自動的に正しいリンク先（`[[システムアーキテクチャ]]`）へ一括置換する選択肢を提示、または自動書き換えを実行する。

## 7. 監査・静的整合性スキャン

### 7.1 来歴 sources と GFM Footnotes の機械的整合性スキャン
LLMによる自動逆合成時、本文中に生成された脚注（`[^drawing-pdf]` など）と、フロントマターの `sources[]` に記述されたIDリストが完全に一致しているかを、`wikid-steward lint` の**静的解析（Pythonコードによる高速スキャン）**によって100%機械的にチェックします。
* **オーファン脚注検知**: 本文中に `[^id]` が存在するが、フロントマターの `sources[].id` に存在しない場合、またはその逆の不整合がある場合、リンターはエラーを検知し警告します。これにより、情報の来歴証明（プロベナンス）の整合性を完全に維持します。

### 7.2 Gitブランチ（PR）戦略と変更履歴のblame証明
AI監視プロセス（`wikid-steward run`）によるコミット＆プッシュは、直接 `main` ブランチではなく **`steward/auto-compiler`** ブランチに行い、PR（Pull Request）として人間に提示します。
これにより、人間がローカルで編集中のファイルと自動処理が競合して「プッシュできない競合」を起こすデッドロックは Git のトポロジーによって完全に解消されます。
最終的に、すべての変更履歴はGitの標準機能である `git diff` で差分確認でき、`git blame` を実行すれば、どの行が AI（`wikid-steward/auto-compiler`）によって自動合成され、どの行が人間（`human:<id>`）によって手書き（手書きメモエリア内）されたのかがバイト単位で100%証明可能です。
