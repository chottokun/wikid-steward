# wikid-steward ＆ SimpleWiki 統合・開発計画書 (v7.0 / GFM＆OKF v0.2 完全対応・アセット空間隔離・自律協調版)

本計画書は、自律成長型ナレッジシステムである `md-wiki` および `wikid-steward` (v5.0) に存在した、複雑な重厚バックエンド（Qdrant 外部ベクトルDB、LangGraph、Docling v2など）のオーバーヘッドを解消し、**「プレーンな GFM Markdown ＋ Git ＋ 超軽量 CLI ＋ SimpleWiki」** の組み合わせによって、陳腐化しにくく運用の摩擦がない、それでいて高い自律性と知識ネットワークを維持する次期開発・統合計画です [28, 34]。

批判的分析と実践的な共同開発シナリオを反映し、単なる機能削減にとどまらない「メタデータ検索」「自律パイプラインの維持」「ブランチ＆PR戦略による人間・AIの編集デッドロック排除」「スタブ専用フォルダ（stubs/）によるステージング昇格運用」「HTML非表示タグによる手書きメモ絶対保護」「AI循環参照遮断フィルター」「GitHub Flavored Markdown (GFM) への完全対応」を取り入れ、現実的で堅牢な形にアップデートしました [4, 11, 21, 22, 112]。

## 1. 基本方針とシステム構成

### 1.1 不要な機能の排除と代替アプローチの導入
* **Qdrant（外部ベクトルDB）の廃止と「軽量構造化メタデータ検索」への移行**: Qdrantによるセマンティック検索は廃止しますが [28, 29]、OKF v0.2が持つ強力なメタデータ（`type`, `tags`）やノート間の明示的な `[[WikiLink]]` 接続関係をインデックス化・パースする **「軽量構造化メタデータ検索（および1-Hopグラフ巡回・文脈合成）」** をSimpleWikiおよびCLI側に実装します [29, 32]。これにより、重いデータベースサーバーを管理することなく、高速で実用的なナレッジ巡回・類似概念の発見が可能です [32]。
* **`_raw` フォルダを起点とする自動処理パイプラインの継承**: 一次資料（PDF、図面、Markdownなど）を `_raw/`（または `staging/`）フォルダに投入するだけで、自動的にテキスト抽出・コンパイルを行うデータフローは不変です [3, 7, 21]。常駐型の重いシステムを持たなくても、後述の軽量CLIのファイル監視機能（`run`）や、Gitフック（GitHub Actions等）と組み合わせることで、以前と変わらぬ「完全自動の自律成長性」を低摩擦で実現します [22]。
* **アセット（メディア画像と原本PDF）のポータビリティ解決確認**: 原本ドキュメントから抽出された画像等のアセットは、すでに `wikid-steward` の既存機能によって **`wiki/assets/{slug}/` に自動抽出され、Markdownからは `![fig1.png](assets/{slug}/fig1.png)` のように、ドキュメントのSlugを冠した名前空間に格納して安全に参照・物理配置されます** [21, 112]。これによって異なる資料間での同名ファイル（`fig1.png`等）の衝突を物理的に完全に防止します。また、これらは `wikid-steward lint` によってリンク切れが自動監査されるため、完全に解決済みです [21]。
* **GitHub Flavored Markdown (GFM) への完全対応**: システムが生成、あるいは処理するすべての Markdown の構文およびフォーマットは、**GFM 規格に準拠**させます [112]。これにより、GitにPushされたMarkdownファイルをGitHubやGitLabなどのWeb UI上で直接閲覧した際、リンクやテーブル、Mermaid、LaTeX数式などが完璧に表示・巡回可能になります。
* **エディタ依存（Obsidian密結合）の完全排除**: 特定エディタのAPIに依存するプラグインUI開発を行わず、VS Code, Neovim, Obsidianなど、使い慣れたあらゆる環境で編集できる「プレーンMarkdown」を正（シングルソース・オブ・トゥルース）とします [28, 34]。

### 1.2 3レイヤーの連携構造
システムは、データの実体（Markdown）と、それを育てるCLI、表示するWebフロントエンドの3つのシンプルなレイヤーで構成されます [34, 121]。

```
┌────────────────────────────────────────┐
│  任意のテキストエディタ / CLI操作      │
└───────────────────┬────────────────────┘
                    │ Markdown直接編集 / CLIによる構造化支援
                    ▼
┌────────────────────────────────────────┐
│  Git リポジトリ (OKF v0.2 Markdown)    │ <--- 知識データの実体（ポータブル GFM）
└───────────────────┬────────────────────┘
                    │ Git Push / Pull (CI/CD自動化)
                    ▼
┌────────────────────────────────────────┐
│  SimpleWiki (Webフロントエンド)         │ <--- 超高速・軽量な閲覧・検索層（Mermaid・数式描画）
└────────────────────────────────────────┘
```

### 2.2 コアエンジン：`wikid-steward` CLI ツール
エディタを選ばず動作する、Python/uv ベースの超軽量なCLIツールとして実装します [6, 22, 28]。

| コマンド | 機能概要 | 実装方針 |
| :--- | :--- | :--- |
| `wikid-steward run` | フォルダを監視し、自動処理を実行する [22]。 | `watchdog` 等の軽量ライブラリを使い、`_raw` への原本投入を契機に、テキスト抽出と `compile` を自律的にトリガーする [22]。 |
| `wikid-steward compile <file>` | メモやテキストから主要概念を切り出し、OKF v0.2形式の新規ノートを自動抽出する [29, 31]。 | プレーンテキストを入力とし、LLM（Gemini等）を用いて用語やその定義を抽出し、適切なフロントマターを付与して保存する。 |
| `wikid-steward compile-stub <term>` | 指定のスタブ（未定義）ノートに対し、バックリンクの文脈から固有定義を逆合成する。 | 循環参照フィルタ（AI生成かつ未査読ノートの除外）をかけた上で、複数ドキュメントからのバックリンク文脈を収集し、LLMに投入してGFM Markdownを逆合成する [4]。 |
| `wikid-steward review <file>` | 人間が内容を確認したノートに対し、フロントマターに `verified` レコードを追加・更新する [29, 31]。 | 指定ファイルの YAML フロントマターをパースし、現在の実行ユーザー名とタイムスタンプを `verified` 配下に自動追記、statusを `stable` に昇格させる [64]。 |
| `wikid-steward resolve <file>` | 手動編集によるGitコンフリクトを自動マージする。 | ファイル内に Git 衝突マーカーが含まれている場合、文脈と一次ソースをベースに競合を自動で解決・マージする [11]。 |
| `wikid-steward lint` | リンク切れやFrontmatter欠損、孤立ノートの監査 [21, 23]。 | シンプルなディレクトリ走査で正規表現マッチ。リンク切れの宛先には、自動でOKF準拠のスタブ（空ノート）を生成・補修する [29, 31]。 |

#### 【自律ルーティング】スタブ専用フォルダ（stubs/）と二段階昇格ライフサイクル
赤リンクから自動起票されたスタブ（`status: draft`）を、最初から本番用のカテゴリフォルダ（`concepts/`など）に散乱させず、**「スタブ専用フォルダ（`wiki/stubs/`）」に一括隔離・集約**して管理します。
1. **隔離ステージ**: `wikid-steward lint` によって自動生成されたスタブノートは、すべて `wiki/stubs/{slug}.md` として作成されます。人間にとって「今から加筆・AIに逆合成させるべきタスクリスト」として明確に機能します。
2. **昇格ルーティング**: バックリンク文脈からの自動逆合成（`compile-stub`）が完了、あるいは人間がレビューして `status: stable`（検証済み）へ昇格させたタイミングで、CLIが `config.yaml` のルーティング定義（例: `type: Concept` ➔ `wiki/concepts/`）に従い、ファイルを本番フォルダへ自動移動させます。

#### 【編集デッドロック解決】ブランチ戦略と Pull Request (PR) 協調モデル
AI自動監視によるコミット・プッシュと、人間のローカルでの手動編集が衝突して競合（デッドロック）を発生させる問題は、Git標準の**ブランチ・PRモデル**によって極めて美しく解決されます。
1. **AI専用ブランチの隔離**: `wikid-steward run` や自動パイプラインによる自動コンパイル・リンク補正結果は、直接 `main` ブランチへコミットするのではなく、自動で **`steward/auto-compiler`** などの一時ブランチを切ってそこにプッシュします。
2. **Pull Requestの自動起票**: プッシュ後、Git Actions等のCIが自動的に GitHub 上で `main` ブランチに対する Pull Request (PR) を作成します。
3. **安全な人間レビュー＆マージ**: 人間は `main` ブランチでローカル競合を一切気にせず編集を進めることができます。AIが自動作成したPRの差分をGitHub上で確認・レビューし、ボタン一つで安全にマージ・統合を制御（Human-in-the-Loop）できます。

### 2.3 閲覧・表現レイヤー：`SimpleWiki` 連携
Gitを介して同期されたMarkdownを、SimpleWikiが高速パースしてレンダリングする際、OKF v0.2の「信頼性シグナル」やGFMの拡張表現をリッチ描画します [34, GFM]。

1. **「Verified（査読済み）」バッジの表示** [122]
   * フロントマターに `verified` レコード（人間による査読ログ `human:...`）が存在する場合、ヘッダーに「✅ Verified by Human」といったトラスト・バッジをUI上に表示します [64, 122]。
2. **鮮度・ステータス警告の自動表示** [122]
   * `status: deprecated` や `stale_after` 期限超過時に、ページ上部に警告ヘッダーを自動で描画します [122]。
3. **「手書きメモ」セクションのハイライト** [122]
   * `<!-- HUMAN BEGIN --> ... <!-- HUMAN END -->` 領域を特別扱いし、テーマカラーに合わせたソフトな背景色やボーダーで囲むなど、AI生成テキストとは明確に区別してレンダリングします [122]。
4. **Mermaid ＆ LaTeX数式 ＆ HTML複雑表のWeb動的描画**
   * Markdownビューワーを拡張し、`mermaid.js` によるSVG構成図描画、`KaTeX` による美麗な数式レンダリング、セルの結合をサポートする HTMLテーブル（`<table>`）のCSSレスポンシブ描画を完全統合します。

## 4. この計画のメリット
1. **GitHub UIとの親和性が100%**: プレーンな Markdown を GFM に統一したことで、Webブラウザ（GitHub UI）から直接リポジトリを開いた際にもWikiリンクやテーブル、数式、Mermaidが崩れず巡回・閲覧可能です。
2. **Gitの力で人間とAIが美しく協調**: ブランチ・PRモデルを採用したことで、常時自動コンパイルが走っていても、人間のローカル執筆体験を阻害する「プッシュ時競合」が根本的にゼロになります。
3. **スタブ専用フォルダによる完璧な秩序**: どこに何の定義があるかが一目でわかり、未定義語がスタブフォルダに美しく一元管理されるため、ナレッジベースのカオス化が完全に防止されます。
4. **メンテナンスフリー**: ベクトルDBのサーバー管理や、LangGraphの複雑な状態遷移エラーに悩まされることがなくなります [28, 32]。
